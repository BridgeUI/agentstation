# 運用手順（復旧のしかた）

ダッシュボード（https://workstation.example.com）か Slack の通知を見て、何が起きているかを切り分け、下の順に対応する。
**原則：軽い手段から。電源断は最後。** 各手順の「誰が」は、本人＝その環境を使っている人、オーナー＝Taro。

## 0. 切り分けの早見表

| 見え方                                | 起きていること                                 | 対応                                                                           | 誰が           |
| ------------------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------ | -------------- |
| ある環境だけ「要確認」、Claude が停止 | その環境の `claude remote-control` が落ちた    | launchd が自動で再起動する。5分待って戻らなければ「Remote Control を立て直す」 | 本人・オーナー |
| 「要ログイン」                        | Claude のログインが切れた                      | 1 へ                                                                           | 本人・オーナー |
| VM が「停止」                         | VM が落ちた（`vm_stop` した覚えがなければ）    | 「VM を再起動」                                                                | 本人・オーナー |
| VM が「起動中」のまま 5 分以上        | ゲストが起動しきらない                         | 「VM を再起動」。繰り返すなら 4 へ                                             | 本人・オーナー |
| VM が「要確認（エージェント停止）」   | VM 内のエージェントだけ止まった                | 「VM を再起動」が手早い。中を見たいなら 2 へ                                   | 本人・オーナー |
| 全環境「応答なし」、SSH は通る        | host のエージェントか GUI セッションが止まった | 2 → 3                                                                          | オーナー       |
| 全環境「応答なし」、SSH も通らない    | Mac か回線が落ちた                             | 5                                                                              | オーナー       |
| 操作が「失敗」                        | 指示の実行でエラー                             | 画面の結果（output）を見る。同じ操作をもう一度。だめなら 2 で中を見る          | 本人・オーナー |
| 操作が「期限切れ」                    | 10 分以内にエージェントが拾えなかった          | 環境が「応答なし」ではないか確認してから、もう一度                             | 本人・オーナー |

## 1. 要ログイン（Claude のログイン切れ）

自動では直らない。SSH で入って `claude auth login` をやり直す。

```bash
ssh <ユーザー名>@<内部IP>   # B（WARP）。A ならブラウザで ssh-<env>.example.com
```

```bash
claude auth login
```

ブラウザで開く URL とコードが表示されるので、その環境の Claude アカウント（A/B/C）でログインする。終わったら Remote Control を立て直す（ダッシュボードのボタンか、下のコマンド）。

```bash
launchctl kickstart -k gui/$(id -u)/com.example.claude-rc
```

期待：3 分以内にダッシュボードが「接続中」になる。

## 2. エージェントが止まった（SSH は通る）

```bash
launchctl print gui/$(id -u)/com.example.agent | grep -E "state|pid|last exit"
```

```bash
tail -50 ~/Library/Logs/agentstation/err.log
```

起動し直す：

```bash
launchctl kickstart -k gui/$(id -u)/com.example.agent
```

期待：1〜2 分で「最終受信」が更新される。`launchctl print` に `state = running` が出ない場合は、plist が読み込まれていない（`docs/setup-mac.md` の launchd の章で `bootstrap` し直す）。

ログの見方：設定ファイルが読めない（`~/.config/agentstation/` の config.json / token.json）、サービストークンの失効（HTTP 403）、`node` のパスが変わった（nodebrew で入れ直したとき）、のどれかが多い。

## 3. GUI セッションが落ちた（ログアウトしてしまった等）

LaunchAgent（エージェント、VM、Remote Control）はログインセッションごと止まる。SSH は通る（cloudflared は LaunchDaemon）。

```bash
who   # console にユーザーがいなければ GUI セッションが無い
```

直し方は再起動がいちばん確実：

```bash
sudo /sbin/shutdown -r now
```

自動ログインで戻り、launchd が全部を立ち上げる。期待：5 分以内に全環境が「正常」。**画面共有で入ったときに「ログアウト」を押さないこと。**

## 4. VM が繰り返し落ちる・起動しない

host に SSH で入り：

```bash
tart list
```

```bash
launchctl print gui/$(id -u)/com.example.tart-vm1 | grep -E "state|pid|last exit"
```

```bash
tail -50 ~/Library/Logs/agentstation-vm/vm1.err.log
```

手で起動して様子を見る（launchd を止めてから）：

```bash
launchctl bootout gui/$(id -u)/com.example.tart-vm1
```

```bash
tart run --no-graphics vm1
```

よくある原因：ディスク残量不足（`df -h /`。VM イメージは `~/.tart/vms/`）、メモリ不足（他の VM を止めてから起動）、イメージの破損（電源断の後。`tart clone` で作り直し、作業内容は git から戻す）。

戻すとき：

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.example.tart-vm1.plist
```

## 5. Mac か回線が落ちた（SSH も通らない）

1. 一覧が「応答なし」で、`https://ssh-host.example.com` にも入れないことを確認する
2. **10 分待つ**（一時的な回線断と区別する。ルーターの再起動なら数分で戻る）
3. 一覧のバナー（Mac mini から n 分間応答がありません）のプラグの様子を見る。**「プラグにも届かない」なら回線かルーターの問題**。ルーターが戻るまで待つ。「消費電力がほぼ 0」なら電源が落ちている、「通電あり」ならエージェントか macOS の問題（先に SSH を試す）
4. Taro の環境 › 操作 › **電源を入れ直す**（オーナーのみ。ホスト名 `host` を入力 → 1 分の猶予 → オフ → 約 1 分 → オン）。ダッシュボードが使えないときは SwitchBot アプリで **オフ → 30 秒 → オン**
5. 3〜5 分待つ。期待：Mac が起動し、自動ログイン → launchd → 全環境が「正常」になる
6. 戻らなければ、SwitchBot アプリでプラグがオンになっているか確認（オンに失敗すると Slack に「操作が失敗」と「手動でオン」の案内が来る）。それでもだめなら実機へ。モニタとキーボードをつないで、起動しているか・ログイン画面で止まっていないか（FileVault が有効に戻っていないか）を見る

スマートプラグについて（`docs/spec.md` 6.1）：

- SwitchBot プラグミニ（JP）。操作するのは Taro だけ。ダッシュボードから（Worker が SwitchBot のクラウド API を呼ぶ。エージェントは関与しない）か、SwitchBot アプリから
- ダッシュボードのボタンは、host の報告が 10 分以上途絶えているときだけ押せる（届いているときは「ホストを再起動」を使う）
- **強制電源断なので、ディスク破損や書きかけファイルの損失があり得る。** VM のイメージは大きいので、復帰後に `tart list` と各 VM の起動（ダッシュボードの報告）を必ず確認する。使うのは、SSH も通らず 10 分待っても戻らないときだけ
- **ルーターや回線が落ちているときは使えない**（プラグ自体が自宅の Wi‑Fi 経由）。その場合はルーターが戻るのを待つか、実機へ
- 前提は「電源が入ったら常に自動的に起動」（`pmset autorestartatconnect 1`。「停電後」だと意図したシャットダウンのあとに戻らない）、自動ログイン（FileVault オフ）、launchd の 3 つ。基礎設定が全部 OK ならそろっている

電源断のあとに確認すること：

```bash
tart list   # 両方 running か
```

```bash
df -h /     # 空き容量
```

各環境の作業フォルダで git の状態を見て、書きかけの変更が壊れていないか確認する。

## 6. ホストの再起動（計画的に行うとき）

ダッシュボードの「ホストを再起動」（オーナーのみ）。ホスト名 `host` を入力 → 1 分の取り消し猶予 → VM を止めて `shutdown -r`。5 分以内に全環境が戻る。
ダッシュボードが使えないときは SSH で：

```bash
sudo /sbin/shutdown -r now
```

## 7.5 スマホから使う（ホーム画面に追加）

ダッシュボードは PWA。ホーム画面に置くとアプリのように開ける（下にタブバー、各環境へのショートカット）。

| 端末                    | やり方                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| iPhone / iPad（Safari） | https://workstation.example.com/ を開いて Access にログイン → 共有ボタン → 「ホーム画面に追加」 |
| Android（Chrome）       | 同じ URL を開いてログイン → メニュー → 「アプリをインストール」（または「ホーム画面に追加」）   |

注意：

- ホーム画面から開いたアプリは Safari / Chrome と別のセッションになるので、初回はもう一度 Access のログイン（Google）を求められる。
- 状態と操作（`/api/*`）はキャッシュしない。オフラインのときは「いまはつながりません」の画面になり、古い状態を見せることはない。
- 画面を作り直したあと（デプロイ後）は、開き直せば新しい画面になる（ネットワーク優先）。それでも古いときはアプリを一度閉じて開き直す。
